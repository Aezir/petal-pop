# 03 技术方案

> 2026-08 更新：完成 Godot vs Web 栈的正式选型评估，结论沿用 Web 栈；技术栈清单细化到库级。

## 1. 选型判断：要不要用 Godot？

**结论：不用。沿用 TypeScript + PixiJS + Tauri。**

判断的出发点不是"哪个技术强"，而是"这个游戏到底是什么"——

> Petal Pop 的核心画面是：一堆图片素材在画布上被拖拽、旋转、缩放、分层、加文字。
> 这不是动作游戏、不是物理游戏，**它本质是一个披着游戏皮的图层编辑器（迷你 Canva）**。
> 编辑器类软件是 Web 技术统治的领域，是游戏引擎的客场。

### 逐项对比（按本游戏的真实需求）

| 需求 | Web 栈 | Godot | 判定 |
|---|---|---|---|
| 图层编辑器交互（拖拽/旋转/层级/面板 UI） | DOM+CSS 做面板是主场 | Control 节点能做但繁琐 | **Web 胜** |
| 文字贴纸、中文排版（海报主题的核心） | CSS/canvas 文本 + 字体生态成熟 | 文本排版能力弱一档 | **Web 胜** |
| 撕取形变 + 镭射闪卡 shader | Pixi mesh + GLSL filter | Polygon2D + shader | 平手（都要手写） |
| 粒子、动态贴纸（二期） | Pixi 粒子够用 | 内置粒子编辑器更顺 | Godot 略胜 |
| 照片转贴纸（二期） | 浏览器有现成 wasm 抠图模型 | 基本要自己造轮子 | **Web 完胜** |
| 打包分发 exe | 需要 WebView2 运行时（见下方缓解） | 单文件自带运行时，发朋友零门槛 | **Godot 胜** |
| 你的成长路线（全栈工程师） | TS/React/渲染/状态管理全部可迁移 | GDScript 只在 Godot 里有用 | **Web 完胜** |
| AI 协作效率 | TS/Web 语料最多，AI 写得最准（AI 友好度的"语料杠杆"） | GDScript 语料少一个量级 | **Web 胜** |
| 手感调参 | 热重载 + tweakpane 调参面板，改参数即时生效 | Inspector 面板也很顺 | 平手 |
| 性能上限 | 浏览器有天花板，但本游戏远用不到 | 上限更高 | 不构成理由 |
| 未来上主机/移动端 | 移动可套 Capacitor，主机基本无路 | 导出管线成熟 | Godot 胜，但护栏里没有这项 |

**7 项定胜负的需求里 Web 拿 5 项**，且拿下的全是每天都要面对的（编辑器、文字、AI 效率、成长路线）；Godot 赢的两项，一项有缓解方案，一项是二期锦上添花。

### Godot 唯一的硬优势怎么化解

Godot 单文件 exe 确实是"发朋友"场景的真优势。Tauri 的缓解方案：**安装包内嵌 WebView2 引导安装器**（Tauri 打包选项勾一下），Win11 自带 WebView2、Win10 自动补装，朋友的体验同样是"双击安装完就玩"。已写进 05 分发计划。

### 什么情况下反悔换 Godot（切换触发条件，白纸黑字）

1. M0 原型在低配笔记本上掉帧，且优化两周无解（预期不会——这游戏渲染压力很小）
2. 玩法方向变了：要做实时动作、物理模拟类的核心玩法
3. 决定上主机（Switch 等）——护栏清单里目前没有这项

只要没触发，就不再重开这个话题。选型反复横跳是独立项目最大的隐形杀手。

## 2. 技术栈清单（库级）

| 层 | 选择 | 干什么 / 为什么 |
|---|---|---|
| 语言 | **TypeScript**（strict 模式） | 类型闭环：数据表、存档、状态全部有类型兜底，AI 写错立刻暴露 |
| 构建 | **Vite** | 热重载秒级，M0 调手感全靠它 |
| 画布渲染 | **PixiJS v8**（WebGL） | 贴纸、撕取 mesh 形变、闪卡 shader、书桌场景 |
| 界面 UI | **React** | 商店、抽奖、图鉴、贴纸盒这些面板用 DOM 做——编辑器软件的正统做法 |
| 状态管理 | **zustand** | 轻量状态库，游戏状态的唯一数据源；React 面板和 Pixi 画布都从它读写 |
| 数据校验 | **zod** | 贴纸表、掉率表、存档 JSON 加载时运行时校验，坏数据当场报错而不是玩到一半崩 |
| 音频 | **howler.js** | 撕纸声随机池、环境音循环 |
| 手感调参 | **tweakpane** | 开发用滑杆面板：撕取阻力、吸附距离、弹跳曲线实时调（发布版剔除） |
| 桌面壳 | **Tauri v2** | 打包 exe、本地存档读写；Rust 层用现成插件，不写 Rust |
| 测试 | **Vitest** | 只测纯逻辑：经济数值、掉率、存档版本迁移——不测画面 |
| 打包 | Tauri bundler → NSIS 安装包 | 内嵌 WebView2 引导安装 |

分工一句话：**画布里的一切归 Pixi，画布外的一切归 React，两边只通过 zustand 说话。**

## 3. 架构草图

```
┌───────────────────────────────────────┐
│ 桌面壳 Tauri（文件存档读写）             │
├───────────────────────────────────────┤
│ React 层（DOM）                        │
│   商店 / 抽奖 / 图鉴 / 贴纸盒 / 设置     │
├──────────────┬────────────────────────┤
│ zustand 游戏状态（唯一数据源）           │
│   拥有的贴纸·零花钱·各画布内容·任务进度   │
├──────────────┴────────────────────────┤
│ PixiJS 层（canvas）                    │
│   书桌场景 → 贴贴台编辑器 → 贴纸精灵     │
│   撕取 mesh / 闪卡 shader / 吸附辅助    │
├───────────────────────────────────────┤
│ 数据表 JSON + zod（贴纸/任务/掉率/价格） │
└───────────────────────────────────────┘
```

核心原则不变：**状态是唯一数据源，画面只是状态的投影**。存档 = 状态序列化成 JSON 写本地（双份写入，带 version 字段做迁移）。

## 4. 关键技术难点

| 难点 | 方案方向 |
|---|---|
| 撕贴纸形变手感 | Pixi mesh 顶点动画；M0 唯一要攻克的东西，tweakpane 调到爽为止 |
| 镭射闪卡 | fragment shader，鼠标位置作 uniform（与知识地图 WebGL/shader 同一棵树） |
| 统一贴贴台 | 编辑器核心与"主题"解耦：主题 = 画布底板 + 素材集 + 辅助规则开关 + 专属工具的注册包 |
| 桌面处处可贴 | 书桌本身就是一张常驻画布，复用编辑器，无特殊逻辑 |
| 房间父子跟随 | 贴在家具上的贴纸挂为家具子节点，Pixi 场景树天然支持 |
| 换装吸附辅助 | 底板标吸附点位，拖近时插值吸引；永远可无视（设计铁律） |
| 导出作品图片 | Pixi renderTexture → PNG |
| 存档防丢 | 双份写入 + version 字段迁移 |
| 照片转贴纸（二期） | 浏览器端 wasm 抠图（现成模型库）→ alpha 膨胀加白边 → 全本地，照片不出电脑 |

## 5. 目录结构（预定）

```
Petal_pop/
├─ docs/
├─ src/
│  ├─ desk/        # 书桌主场景（存钱罐/星星罐/书立/桌面画布）
│  ├─ editor/      # 统一贴贴台：选中工具、图层、吸附、裁切
│  ├─ themes/      # 海报 / 换装 / 房间——每个主题一个注册包
│  ├─ systems/     # 经济 / 任务 / 图鉴 / 存档
│  ├─ ui/          # React 面板：商店、抽奖、图鉴、贴纸盒
│  └─ data/        # 贴纸表、任务表、掉率表、价格表（JSON + zod schema）
├─ assets/         # 按 02-art.md 命名规范
└─ tools/          # 素材处理脚本（批量抠图、图集打包）
```

**数据驱动**不变：加新主题 = 加素材 + 填表 + 写一个主题注册包，编辑器核心不动。
